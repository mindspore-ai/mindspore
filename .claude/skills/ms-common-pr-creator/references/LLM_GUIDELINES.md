# LLM Analysis Guidelines

Guidelines for analyzing code changes and generating PR descriptions.

## Contents

- Git commands for analysis
- Template-driven body generation
- Content quality guidelines
- Examples: good vs bad

## Git Commands for Analysis

```bash
# Get commit messages to understand PR intent
git log upstream/<target_branch>..HEAD --reverse --oneline

# Identify changed files
git diff upstream/<target_branch>...HEAD --name-only
git diff upstream/<target_branch>...HEAD --stat
```

Focus on key implementation files (avoid tests, build files unless relevant).

## Template-Driven Body Generation

The PR body is generated by filling in a template file. The template contains two kinds of content:

1. **Fixed structure** — everything outside `{{FILL:...}}` markers. This includes HTML comments,
   section headers, checklists, `/kind` lines, URLs, and any other text. Copy it verbatim,
   character for character.

2. **Fillable zones** — `{{FILL: instruction}}` markers. Replace each marker (including the
   `{{FILL:` and `}}` delimiters) with generated content following the instruction inside.

### Why strict compliance matters

Templates contain specific keywords and structural patterns that CI bots and review bots parse
to determine PR status and preconditions. For example:

- `/kind feature` tells the bot which label to apply — changing the format (e.g., adding quotes,
  altering whitespace) can cause the bot to miss it
- Section headers like `**What type of PR is this?**` may be parsed as delimiters
- Checklist items with `+ - [ ]` are checked for completeness — if the LLM changes `[ ]` to `[x]`,
  it falsely claims the author has self-reviewed, which is deceptive
- HTML comments (`<!-- ... -->`) contain contributor guideline URLs and label lists that bots parse —
  removing them silently breaks onboarding flows

Altering, omitting, or reordering any fixed content can break these automated checks, blocking
CI or merge. The safest approach: treat everything outside `{{FILL:...}}` as immutable.

**Common mistakes to avoid:**
- Starting the output with `---` (YAML frontmatter leaking into the PR body)
- Removing normal `<!-- ... -->` HTML comments that belong to the template
- Leaving an agent-only comment in the final output, or deleting only part of that line

### Agent-only comment rule

Treat template comments in two categories:

1. **Agent-only comments** — use the exact format `<!-- AGENT_INSTRUCTION — ... -->`.
   These comments are instructions for generation only. Make each one end with the exact
   sentence `最终 PR 正文中不要包含这条注释。` so leakage is easy to detect. Read them,
   follow them, then delete the entire comment line from the final PR body.

2. **Normal template comments** — every other `<!-- ... -->` comment is real PR-template content.
   Preserve these comments verbatim because bots and reviewers may depend on them.

The key distinction is simple: agent-only comments are consumed during generation and must not
appear in the final PR body; normal template comments remain.

### Generation process

1. Start with the template content **after the YAML frontmatter** — skip the `---` block at the
   top (it contains `projects:`, `default:` etc.). Never start with `---`
2. For each `{{FILL: instruction}}` marker, analyze the code changes and generate content
   that follows the instruction
3. Replace the marker with the generated content — nothing more, nothing less
4. **Consume agent-only comments** — if you see `<!-- AGENT_INSTRUCTION — ... -->`, obey the
   instruction and then remove the entire `<!-- ... -->` line from the output. Do not leave
   the comment in place. Do not delete only part of the line.
5. Verify the final output:
   - All original structure, headers, comments, and checklists are intact
   - All normal `<!-- ... -->` HTML comments are preserved verbatim
     (they contain URLs and label lists that CI bots parse)
   - Every agent-only comment's instruction was followed (e.g., checklist-preserve instruction →
     all `[ ]` items remain with empty brackets)
   - No agent-only comment remains in the output: no `AGENT_INSTRUCTION`

### Final cleanup step

Before writing the PR body file, scan the completed output once from top to bottom and remove
every remaining `<!-- AGENT_INSTRUCTION — ... -->` line. Treat this as a required final pass,
not an optional cleanup.

### Content language

All generated content (the text replacing `{{FILL:...}}` markers) must be in **Chinese (中文)**.

### PR type determination

When a `{{FILL:...}}` marker asks to choose a PR type, determine it from commit messages first:

| Type | Keywords |
|------|----------|
| **feature** | `feat`, `feature`, `add`, `implement`, `new` |
| **bug** | `fix`, `bug`, `hotfix`, `patch`, `issue` |
| **task** | `chore`, `task`, `update`, `improve`, `doc`, `optimize` |
| **refactor** | `refactor` |
| **clean_code** | `clean`, `cleanup` |

If commit messages are ambiguous, analyze the code changes:

- New files / new functions / new functionality → **feature**
- Changes to error handling, corrections to existing logic → **bug**
- Documentation, tests, build configs, dependency updates → **task**
- Restructuring without behavior change → **refactor**

### Summary content guidelines

When a `{{FILL:...}}` marker asks for a PR summary or description, structure the content as:

- **PR 目的** — why this change is needed (1-2 sentences)
- **主要方案** — high-level approach and implementation strategy (2-3 sentences)
- **主要修改点** — key changes organized by module/component, using tables for multi-file changes

Use Markdown formatting (headers, tables, bullet lists) as appropriate. Choose the level of
detail based on the change scope — a 3-file bug fix needs less detail than a 20-file feature.

### When to use visualizations

- **Mermaid diagrams**: Architecture changes, data flow, state transitions
- **Markdown tables**: Multi-file changes, API changes, configuration changes

## Examples

Below are concrete examples showing good vs bad content for the fillable zones.
These illustrate the difference between a useful description that helps reviewers,
and a low-quality one that just restates file names.

### Example 1: Bug fix (3 files changed)

Commit message: `fix(pass): handle null pointer in fusion pass`

**Bad** — restates file names, no insight for reviewers:

```markdown
### PR目的
修复空指针问题。

### 主要修改点
- 修改了 fusion_pass.cc
- 修改了 fusion_pass.h
- 修改了 fusion_pass_test.cc
```

**Good** — explains root cause, approach, and impact:

```markdown
### PR目的
修复 FusionPass 在处理动态 shape 算子时，因输入 tensor 为空导致的空指针崩溃问题（issue #1234）。

### 主要方案
在 `FusionPass::Run()` 入口处增加输入 tensor 的空值检查，对空输入提前返回并记录 warning 日志，
避免后续 `GetShape()` 调用触发 segfault。

### 主要修改点
#### FusionPass 模块
| 文件 | 修改内容 |
|------|---------|
| fusion_pass.cc | `Run()` 方法入口增加空 tensor 检查，空输入时返回 `SUCCESS` 并打印 warning |
| fusion_pass.h | 新增 `IsValidInput()` 私有方法声明 |
```

### Example 2: Feature (8 files changed)

Commit message: `feat(dvm): add tiling strategy for conv2d operator`

**Bad** — too vague, reviewers learn nothing:

```markdown
### PR目的
添加新的 tiling 策略。

### 主要方案
新增了相关文件并修改了现有代码。

### 主要修改点
- 新增 conv2d_tiling.cc 和 conv2d_tiling.h
- 修改 tiling_manager.cc
- 修改 op_registry.cc
- 相关测试文件
```

**Good** — conveys design intent and key decisions:

```markdown
### PR目的
为 Conv2D 算子实现多级 tiling 策略，支持在 L1/L0 两级缓存上进行数据切分，
是大 feature size 场景下性能优化的基础。

### 主要方案
采用"先切 H 维度再切 W 维度"的两级切分策略。在 TilingManager 中注册新策略，
通过 OpRegistry 将 Conv2D 算子与该策略绑定。tiling 参数根据硬件 L1/L0 缓存大小
动态计算，确保每级切片不超出对应缓存容量。

### 主要修改点
#### Tiling 核心逻辑（新增）
| 文件 | 修改内容 |
|------|---------|
| conv2d_tiling.h | 定义 `Conv2dTilingStrategy` 类，继承 `TilingStrategyBase` |
| conv2d_tiling.cc | 实现 `CalcTiling()` 核心方法：L1 级按 H 维切分，L0 级按 W 维切分 |

#### 框架集成
| 文件 | 修改内容 |
|------|---------|
| tiling_manager.cc | `RegisterStrategy()` 中注册 Conv2D tiling 策略 |
| op_registry.cc | 将 Conv2D op type 绑定到新策略 |
```

### Example 3: Test plan

**Bad** — generic, no specific information:

```markdown
已测试，功能正常。
```

**Good** — clear scenario coverage:

```markdown
- 新增单元测试 `test_conv2d_tiling_l1_split` 和 `test_conv2d_tiling_l0_split`，
  分别验证 L1 级和 L0 级切分逻辑的正确性
- 功能测试：使用 input shape [1, 64, 224, 224] 的 Conv2D 算子验证端到端 tiling 结果
- 边界测试：验证 feature map 小于单级缓存容量时不进行切分
- 性能测试：对比 tiling 前后的算子执行耗时，确认无性能回退
```

## Quality Guidelines

- **Be concise**: Focus on what reviewers need to know
- **Be specific**: Mention actual functions, classes, patterns changed
- **Use Chinese**: All generated content should be in Chinese
- **Avoid noise**: Don't list every line change, focus on intent and impact
- **Explain "why"**: Reviewers can read the diff to see "what" changed; the summary should explain why the change is needed and the approach taken
